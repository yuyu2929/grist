# Grist 开发日志

按时间顺序记录开发过程中发现并修复的**真实 bug**——包括三个在核心算法定型前
发现的深层错误。每条包含：症状、根因、修复、教训。测试套件中的对应测试名
已注明，这些测试的存在就是为了让这些 bug 不能复活。

---

## BUG 1 — 扫掠方向错误（覆盖核，最深层）

**症状**：方 + 洞的简单案例，洞被完全忽略，总面积 100（应为 84）。

**根因**：活动边扫掠按行自上而下处理，此时 `ya`（行底）递减，"边已死"的条件
`ymax < ya` 非单调——底部边在顶行被永久移除后无法回归（指针已越过），且会
造成虚假的"活动边为空"认证，把整行误填为全覆盖。认证条带逻辑依赖的正是
"活动边集单调"这一前提，方向错了整个认证机制都是错的。

**修复**：改为自底向上扫掠（`range(j1, j0-1, -1)`），此时 `yb`/`ya` 均递增，
进入（`ymin <= ya`）与退出（`ymax < ya`）条件同时单调，认证条带才真正成立。

**教训**：扫掠线算法的单调性不是风格问题，是正确性前提。写之前先在纸上
画两个方向的指针运动。对应测试：`test_coverage.py::test_square_with_hole_even_odd`。

## BUG 2 — 未认证条带的理论错误（覆盖核，理论级）

**症状**：圆过计数 +0.26（逐格误差 0.0825）；轴对齐多边形全部通过——
测试被"骗过"。

**根因**：原设计在未认证条带内于 `yc`（条带中线）处采样一次覆盖区间。这对
`I(y)` 随 y 变化的形状（斜边、曲边）不精确——圆在条带内各行的覆盖区间
宽度不同，中线采样系统性高估。轴对齐多边形的 `I(y)` 恰好恒定，所以简单
测试全绿，错误被掩盖了很久。

**修复**：未认证条带改为**精确路径**：条带裁剪 + 逐格奇偶测试 + 边界格
精确裁剪（Sutherland–Hodgman + 定向归一化后的签名 shoelace 求和）。理论
文档同步改写：原引理 2（错误）→ 引理 2'（证明该近似误差 ≤ m·h²/2）+
引理 3（定向归一化保证异或面积 = 签名 shoelace 和）。

**教训**：测试数据要包含"性质会随维度变化"的案例（斜边），不能只用
轴对齐图形——后者会让近似算法假装精确。对应测试：
`test_coverage.py::test_rotated_square`、`test_fuzz_random_polygons`。

## BUG 3 — 行映射的 epsilon 陷阱（Grid）

**症状**：边界线（恰好落在格线上的线）全长丢失，total = 0。

**根因（第一版修复也是错的）**：`floor((ytop-y)/c)` 对落在行顶边的 y 差一行。
第一次修复加了绝对 epsilon：`y >= ytop - j*c - 1e-9*c` 时行号减一。这引入了
新 bug——`j=0` 时条件变成 `y >= ytop - 1e-9*c`，任何在顶边下方 1e-9·c 范围内
的 y（含 ulp 级噪声）都被映射到第 -1 行。绝对 epsilon 无法区分"恰在顶上"
和"比顶边低一个 ulp"。

**修复**：去掉 epsilon，直接用边界值比较：`j = floor(t); if y >= ytop - j*c: j -= 1`。
y 恰在行顶边（含浮点噪声造成的 t=j±ulp）都归上一行；严格在行内的 y 归本行。
两种噪声情形都归到一致的行，测度划分保持。

**教训**：修浮点边界 bug 时，先问"这个 epsilon 在哪个参数取值下会反过来
咬人"。对应测试：`test_grid.py::test_row_of_exact_boundaries`。

## BUG 4 — 瓦片头部 struct 不匹配（序列化）

**症状**：`struct.error: pack expected 6 items for packing (got 7)`。

**根因**：`_HDR = struct.Struct("<4sIIIII")` 是 6 项，`canonical_bytes` 却传了
7 个值（把格数也塞进了头部）。头/体边界靠手工对齐，没有单一事实来源。

**修复**：格数独立为 `_CNT`，编码/解码对称修改。

**教训**：二进制格式里，头部字段数和 pack 调用点必须成对出现、成对修改。

## BUG 5 — 增量更新的字节非确定性（金字塔）

**症状**：`update(1 要素)` 后与全新烘焙逐格相同，但**字节不同**——而"更新后
与新鲜烘焙字节级相同"是设计承诺。

**根因**：`_rebuild_parent` 迭代子瓦片时用 `cells.items()`（字典插入序），
当四个子格同属一个瓦片时合并序为排序序 (i,j),(i,j+1),(i+1,j),(i+1,j+1)，
而 `_aggregate_level` 的规范序是 (0,0),(1,0),(0,1),(1,1)。浮点求和顺序敏感，
1 ulp 差异 → 不同 blake2b → 不同字节。

**修复**：`_rebuild_parent` 改为按粗格组织、每个粗格严格按规范子格序合并
（跨瓦片也保持序）。

**教训**："语义等价"不等于"字节等价"。内容寻址系统里字节就是身份，
任何顺序敏感的浮点累加都必须钉死顺序。对应测试：
`test_pyramid.py::test_update_add_equals_fresh`。

## BUG 6 — 空瓦片 never 被更新（增量）

**症状**：编辑落在原本空的区域，新要素的格子不出现；与新鲜烘焙差 13 个瓦片。

**根因**：`update()` 的受影响扫描只遍历 `self.levels[0]`——manifest 里**存在**
的瓦片。新要素触及的空瓦片不在 manifest 里，永远不会被标记受影响。

**修复**：扫描完整瓦片网格（`tile_grid(0)`），而非已存在的瓦片。

**教训**："遍历存在的"和"遍历可能被影响的"是两回事。manifest 是稀疏的，
任何以 manifest 为全集的反而是漏的。

---

## BUG 7 — 孤儿 blob 泄漏进文件（序列化）

**症状**：同 BUG 5 的字节不一致（瓦片全部相同，文件却不同）。

**根因**：内容寻址 store 在 update 后保留被替换的旧瓦片（这是 diff 能力
所需要的），但 `serialize` 把整个 store 写进文件——旧 blob 泄漏。

**修复**：`serialize` 只写 manifest 引用的 blob（`TileStore.referenced`）。
文件即活集；内存里的 store 仍可保留孤儿供 diff。附带好处：文件更小。

**教训**：区分"存储器的内容"和"序列化的内容"。前者可以宽松（支持 diff），
后者必须规范（支持字节级身份）。

## BUG 8 — Ed25519 基点用错（企业层）

**症状**：RFC 8032 测试向量验证失败。

**根因**：基点的 y 坐标写成了另一个公式变体的值 `6·2^230+8`（某 twisted
Edwards 实现里的常数），RFC 8032 的基点是 `4/5 mod p`。两个都是"某个
Edwards 曲线的基点"，但曲线参数 d 必须与基点匹配。

**修复**：`_BY = 4 * pow(5, p-2, p) % p`。修正后与 `cryptography` 库
交叉验证 5 组随机密钥 × 3 种消息长度全部一致。

**教训**：密码学常数不能凭记忆写；用官方测试向量 + 参考实现交叉验证。
对应测试：`test_enterprise.py::test_ed25519_roundtrip`。

## BUG 9 — `has("")` 永远为假（企业层）

**症状**：刚签发的许可证立即报 "license expired"。

**根因**：`verify_license` 用 `lic.has("")` 检查有效期——空字符串永远不在
feats 里。把"有效期检查"误用成了"功能检查"。

**修复**：拆出 `License.is_valid(now)`，`has()` 内部调用它。

**教训**：空值/哨兵值复用是 bug 温床；每种检查一个语义明确的入口。

## BUG 10 — 并行烘焙的 pickle 失败（企业层）

**症状**：`AttributeError: Can't pickle local object`。

**根因**：`ProcessPoolExecutor.map` 的参数函数是闭包（局部函数），
multiprocessing 无法 pickle。

**修复**：提取为模块级 `_band_acc(band, grid_params)`，worker 内重建 Grid
（只传纯数值参数）。

**教训**：multiprocessing 的边界上只过模块级函数和可 pickle 数据。

---

## BUG 11 — `from_acc` 丢失要素表（企业层）

**症状**：并行烘焙结果与串行逐格相同、文件却不同。

**根因**：`Pyramid.from_acc` 构造时 `features={}`——并行路径算完了覆盖却
丢了要素几何，序列化出的 .grist 没有要素表（无法再 update/verify）。

**修复**：`from_acc` 接收 features 参数；`bake_parallel` 传入
`{f.fid: f for f in feats}`。

**教训**："构建结果"和"构建上下文"要一起传。测试断言字节相等才能发现
这类静默丢失（逐格比对发现不了）。

## BUG 12 — 受影响瓦片扫描的设计错误（增量）

**症状**：600 要素数据集里编辑一个小方块，增量比全量还慢（0.5×）。

**根因**：`update()` 把"所有要素触及的瓦片"当受影响集——等价于全部非空
瓦片，每次更新都重算全部要素的覆盖。受影响应该是**被编辑要素触及的瓦片**；
其他要素只需要为这些瓦片提供覆盖（且每个只算一次）。

**修复**：三重分解——(1) 脏瓦片 = 编辑要素 bbox 触及的瓦片（保守 ±1）；
(2) 覆盖缓存 = 只算与脏瓦片重叠的要素，每个一次；(3) 向上传播只沿
真实变化的瓦片。稀疏编辑场景 **70×** 加速。

**教训**：增量计算的成本模型要在设计时写下来（docstring 里的 Cost model），
否则"局部更新"会悄悄退化成全量。

## BUG 13 — 瓦片内坐标用了绝对坐标（内容寻址）

**症状**：重复图案（如同一要素的两个相同部件）不去重，存储偏大。

**根因**：瓦片字节里存的是层内绝对格坐标，且头部含瓦片位置——两个位置不同、
内容相同的瓦片字节必然不同。内容寻址的"内容"被位置污染了。

**修复**：瓦片内格坐标改为**瓦片相对**（`i % T`），位置只存在于 manifest。
重构触及 `level_cell`/`_rebuild_parent`/`_build_level`/`_rebuild_tile0`/
`csv_cells` 五处。

**教训**：去重系统的第一问是"什么进哈希"。把位置这类外在属性混进内容哈希，
去重率直接归零。

## BUG 14 — Feature 结构无校验，错误 nesting 静默 corruption

**症状**：基准脚本构造 `polys=[ring]`（少包一层：环当成了多边形部件），
直到很远的 `bbox()` 才以 "cannot unpack non-iterable float" 崩溃，
排查方向被带偏。

**根因**：`Feature.__init__` 直接存嵌套列表，不验证结构。最常见的构造错误
（裸环当部件）会静默通过，在下游以费解的形式爆炸。

**修复**：`_check_structure()` 在构造时验证 points/lines/polys 的配对与
嵌套深度，违反立即抛带说明的 ValueError。

**教训**：对"容易构造错"的数据结构，fail-fast 校验省下的排查时间远超
校验本身的开销。

## BUG 15 — 域边界的质量静默丢失（fit_grid 语义陷阱）

**症状**：demo 的线守恒差恰好 9.0——一条道路的水平段顶点恰在 y=100.0，
即网格顶边。

**根因（设计层，非计算错误）**：网格域是半开的 [x0,x1)×[ybot,ytop)，
`fit_grid(pad=0)` 把域边恰好放在数据 bbox 上，任何与 bbox 极值重合的
几何，其边界重合部分落在域外，测度静默丢失。计算完全正确（半开规则的
应有行为），但"栅格化我的数据"的用户预期的是全量保持。

**修复**：~~保留 `pad=0` 默认（cell_count 契约精确不变），但在 docstring
明确警告；demo 与文档建议数据可能触边时传小 pad（如 extent 的 1e-6）。
域定义是用户的显式选择，库不偷偷改网格。~~
**已被 BUG 18 修订**：默认值改为自动 pad（1e-9 相对余量），`pad=0`
降级为显式退出。本条记录的根因分析与"半开语义在域拟合时反噬"的
教训不变；变更见 BUG 18。

**教训**：半开/闭区间语义在"域由数据拟合"时会反噬——域边界与数据边界
重合不是巧合而是常态（裁剪瓦片、合成数据生成器）。文档必须写清楚。

## BUG 16 — totals() 不确定性：守恒检查自身依赖 dict/set 序

**症状**：`tests/test_enterprise.py` 的 `test_parallel_bake_equals_serial`
约 40% 概率失败，失败信息是裸 assert（无消息）；单独重跑又过。
序列化字节一致，`totals()` 不一致。

**根因**：`Pyramid.totals()` 用 `for h in set(self.levels[0].values())`
迭代瓦片、用 `.cells.values()` 按插入序迭代格值，然后 `+=` 累加。
- set 的迭代序依赖 bytes 哈希，而 **PYTHONHASHSEED 每进程随机**；
- cells 的插入序取决于建造路径：串行烘焙按 fid 排序的特征序插入，
  并行 band 合并按 band 序插入——内容相同、顺序不同。

两者叠加：浮点求和序随进程 seed 与建造路径变化，1 ulp 差异时隐时现。
**这是最危险的一类 bug：被检查对象（金字塔）是确定的，检查工具本身
不确定**，而且只在约四成进程中显形。

**修复**：瓦片按 hash 排序迭代、格按 (i,j) 排序迭代、每类测度用
`math.fsum`（精确舍入，与排列无关）。`cli.py` 的 verify 期望值同样
改为 sorted + fsum。新增回归测试
`test_totals_deterministic_under_permuted_construction`：用
{1.0, 1e16, -1e16} 三个构造值使旧实现**确定性**失败
（朴素求和序 A 得 0.0、序 B 得 1.0），新实现两序均精确得 1.0。

**教训**：凡是"对浮点数求和"的代码，只要迭代源是 set/dict 且未排序，
就把不确定性引进了本该确定的结论。守恒校验、基准指标这类"裁判代码"
要先用裁判标准审查自己。

## BUG 17 — 测试硬编码绝对路径，解压自包含性被静默破坏

**症状**：grist.zip 解压到干净目录后跑 `tests/run_all.py` 失败——
但失败的不是解压出来的代码：7 个测试文件与 bench.py 全部
`sys.path.insert(0, "/workspace/grist")`，导入的是**原始目录**的库。

**根因**：开发期为了在任意 cwd 下能跑，写死了绝对路径。单仓库开发
无感，一旦打包分发，zip 里的测试测的是 zip 外的代码——自包含验证
完全失效，且失败模式是"莫名其妙地过/莫名其妙地挂"，极易误判。

**修复**：8 个文件统一改为
`sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))`
（与 demo/run_demo.py 一致）。批量替换时 `import os` 被插到了
bench.py 的 `from __future__ import annotations` 之前导致 SyntaxError
（ast.parse 不查 future 位置，只有 py_compile/运行才报）——已修复，
并把 py_compile 全量编译纳入验证流程。

**教训**：路径相关的"开发便利"是打包期的技术债。自包含验证不能只
看"测试通过"，要确认被测代码的 `__file__` 确实来自解压目录。

## BUG 18 — 默认 CLI 路径过不了自己的 verify（BUG 15 的设计修订）

**症状**：`grist bake demo/city.geojson -o out.grist --cell 0.5` 后
`grist verify out.grist` 报 `line: err=9.0 MISMATCH`。旗舰完整性检查
在默认路径上失败。

**根因**：不是计算错误，是 BUG 15 的决策后果。当时选择"保留 pad=0
默认、文档警告"，但默认路径 = 数据 bbox 恰好等于半开域 → 任何贴边
几何（demo 里终点在 y=100 的道路）静默丢测度。用户视角：库的核心
承诺（守恒）在开箱路径上不成立。

**修复（修订 BUG 15 的决策）**：`fit_grid` 的 `pad` 默认从 `0.0` 改为
`None` = 自动 padding（域尺寸的 1e-9，绝对下限 1e-12）。半开域宽 W
在数学上不可能严格包含跨度 W 的闭数据，所以"域覆盖数据"必须有余量；
1e-9 相对余量让守恒精确成立，代价是域宽多 1e-9。精确倍数场景
（如 extent 100 + cell 0.5）会多出 1 行/列——那格不多余：贴边几何
只能住在那里。`pad=0.0` 保留为显式退出（语义见 BUG 15）。
CLI `--pad` 默认同步改为 auto，help 写明两种语义。

**教训**：文档警告不能替代默认值正确。当"文档化的陷阱"恰好落在
产品的主路径上，正确做法是改默认值，而不是让用户背文档。

## BUG 19 — bbox_cells 把"含在域内"的左/底边当成域外

**症状**：显式 `Grid(0, 10, 1, 10, 10)` 上，位于底边 y=0 的线段
覆盖为 0（贴左边的几何同理）。

**根因**：`bbox_cells` 的域外测试 `bx1 <= x0 or by1 <= ybot` 对左/底
边用了 `<=`。半开域是 [x0,x1)×[ybot,ytop)：左/底边**包含**，右/顶边
**排除**。所以"结束恰在 x0/ybot"的 bbox 依然与域相交，`<=` 却判了
域外。`point_cell` 的测试（`x0 <= x < x1`）是对的，两处不一致。

**修复**：改为 `bx1 < x0 or by1 < ybot`（严格小于才算出界）。

**教训**：半开约定要写成一条规则贴在每个边界判断旁边（含/不含各是
哪条边），而不是靠记忆。同一条规则在两个函数里写反一半，比全写反
更难发现——因为大多数数据不贴边。

## BUG 20 — totals() 按不同 blob 计数，去重把守恒检查吃掉了

**症状**：100×100 正方形烤到 128×128 网格（cell≈0.78125），
`totals()["polygon"]` = 9218.75，差 781.25。

**根因**：`totals()` 遍历 `set(self.levels[0].values())`——**不同
blob 的集合**。内容寻址存储下，多个位置的相同瓦片共享一个 blob
（这正是存储优化：64 个引用 / 59 个 blob）。按 set 遍历等于每个
不同内容只算一次，少计的部分恰好等于去重省下的部分：5 个共享瓦片
× 256 格 × 0.6103515625 = 781.25，分毫不差。
**存储优化静默腐蚀了验证它的检查**——而且数据越规则（去重越多），
偏差越大；随机数据（基准用的）几乎不去重，所以基准全线"正常"。

**修复**：按 manifest **引用**遍历（`levels[0].values()`，含重复），
排序后用 fsum 求和。同步修复 demo 与 test_pyramid 里同款写法。

**教训**：内容寻址 + "校验和"类代码是陷阱组合：任何"对瓦片求和"的
导出量必须按引用计数，不能按 blob 计数。写测试要故意造高去重数据
（大而均匀的图形）——随机模糊测试永远测不到这一面。
